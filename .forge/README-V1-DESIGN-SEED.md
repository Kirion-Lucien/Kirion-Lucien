## 1. Objective

Lucien's profile must function as a public showcase of interface judgment.

The page should demonstrate, before it claims, competence in:

- information hierarchy;
- visual priority;
- spacing and density control;
- responsive composition;
- accessibility;
- interaction/state thinking;
- design-system discipline;
- frontend presentation;
- content restraint.

Primary acceptance question:

> If every explicit reference to "UI/UX" and "Interface Specialist" were removed, would the profile still look like it was designed by someone who understands interfaces?

If the answer is no, the candidate is REWORK.

## 2. Experience goal

The intended visitor progression is:

1. immediate recognition of a distinct Lucien identity;
2. clear understanding that Lucien is the Smithy's interface specialist;
3. evidence that the specialization extends beyond visual styling;
4. visible breadth across different system frames;
5. confidence that the profile itself practices the standards it states;
6. awareness that deeper frontend/UI/UX training assets are still being forged.

The profile must feel:

- quiet;
- deliberate;
- warm;
- structured;
- precise;
- GitHub-native.

It must not feel like:

- a simulated SaaS dashboard;
- a cyberpunk HUD;
- a badge collection;
- a generic frontend portfolio template;
- a fake product surface pasted into GitHub;
- a generated screenshot presented as finished interface design.

## 3. Platform model

GitHub is the application shell.

GitHub owns:

- account chrome;
- navigation;
- repository tabs;
- link styling;
- native typography;
- responsive page behavior;
- repository presentation.

The README owns:

- Lucien identity;
- information architecture;
- one primary hero;
- chapter hierarchy;
- restrained branded accents;
- safe public specialization details.

The implementation should cooperate with GitHub instead of recreating another application inside it.

## 4. Visual system

### Palette

- OBSIDIAN — #0B0C0F
- GRAPHITE — #15140F
- WARM WHITE — #F4F1E8
- AMBER — #F5C451
- PALE GOLD — #FFE09A
- DEEP GOLD — #B98518

Target distribution:

- 80–85% dark neutrals;
- 10–15% warm white / metallic neutrals;
- 5–8% amber/gold signal.

Amber is semantic emphasis, not wallpaper.

### Character language

Lucien's visual language is:

`frames · hierarchy · flow · states · clarity · restraint`

Canonical character direction:

- black / very dark brown hair;
- warm amber eyes;
- graphite / black technical-casual clothing;
- restrained gold stitching or hardware;
- composed, observant expression;
- warm technical studio rather than server-room aesthetic;
- rectangles, layout frames, grids, and baseline geometry used subtly.

Avoid tactical-anime armor, excessive buckles, fantasy motifs, neon cyberpunk effects, or decorative technology glyphs.

## 5. Hero specification

The hero is a brand composition, not a fake interface screenshot.

Recommended master ratio:

- approximately 1800 × 560;
- widescreen;
- Lucien positioned toward the right 38–42%;
- left side retains real negative space for deterministic typography.

Image generation, if used, may provide only:

- Lucien;
- environment;
- lighting;
- texture;
- non-legible interface atmosphere.

Generated imagery must not be trusted to render final typography, labels, code, GitHub UI, repository cards, or readable product copy.

Final hero text must be placed deterministically after the artwork is created.

Maximum hero copy:

```text
KIRION — LUCIEN
INTERFACE SPECIALIST
UI/UX SYSTEMS · FRONTEND ENGINEERING
interfaces that explain themselves.
```

No additional paragraphs or miniature interface labels inside the hero.

Important information must remain available as native README text even if the hero fails to load.

## 7. Information architecture

The V1 README is limited to five chapters.

Narrative:

`identity → expertise → range → craft → future`

### 01 — INTERFACE

Purpose: identify Lucien and establish the specialization.

Target copy shape:

```md
## 01 — INTERFACE

**Lucien Marek Sol**

Interface Specialist of **The Kirion Smithy**.

I shape the layer where people meet systems — structure, interaction, visual hierarchy, responsive behavior, accessibility, and frontend implementation.

**Clarity is part of correctness.**
```

This is not a biography or résumé section.

### 02 — DISCIPLINES

Six disciplines only:

```text
01 · UI / UX SYSTEMS
     structure · flows · states

02 · FRONTEND ENGINEERING
     implementation · behavior · integration

03 · INFORMATION ARCHITECTURE
     organization · priority · navigation

04 · DESIGN SYSTEMS
     tokens · patterns · components

05 · INTERACTION DESIGN
     feedback · motion · transitions

06 · ACCESSIBILITY
     semantics · focus · inclusive use
```

Prefer a resilient indexed vertical presentation over a fragile multi-column card grid.

The discipline list must remain readable without custom layout tricks.

### 03 — FRAMES

Purpose: demonstrate that Lucien is not limited to one frontend shape.

Public system-frame taxonomy:

```text
PUBLIC SERVICE
OPERATIONS
MOBILE
DESKTOP
DATA-DENSE
REALTIME
KIOSK / POS
OFFLINE / DEGRADED
```

Anchor statement:

> One interface discipline. Different operating constraints.

Optional supporting copy should remain short and explain that different systems carry different density, input, failure, and accessibility constraints.

### 04 — CRAFT

Public interface principles:

- Hierarchy before decoration.
- State before animation.
- Accessibility before cleverness.
- Consistency before novelty.
- Evidence before preference.

Restrained implementation surface:

```text
HTML · CSS · JavaScript · TypeScript · React
components · tokens · state · responsive systems · testing
```

Do not expand this into a technology-logo wall.

Technologies not yet supported by actual training/work evidence should not be presented merely because they are common frontend tools.

### 05 — UNDER FORGE

Future specialization infrastructure is visible but must not be misrepresented as complete.

```text
FRONTEND UI/UX FORGE
UNDER FORGE

Practical interface training across responsive frames, application classes,
component architecture, interaction states, accessibility, and frontend implementation.

UI/UX MASTER
UNDER FORGE

Durable reference for interface architecture, information hierarchy,
interaction patterns, design systems, accessibility, and frontend craft.
```

Closing line:

> The specialization is still being sharpened.

Names become repository links only after the repositories actually exist and are intentionally public.

## 9. Typography

README body typography remains GitHub-native.

Custom typography is reserved for the hero.

Hero voices:

- primary identity: elegant condensed / monumental serif;
- secondary technical labels: clean grotesk or monospace.

Do not turn the README body into a typography experiment.

## 10. Spacing and density

Conceptual rhythm:

`8 · 16 · 24 · 40 · 64`

This is a relationship guide, not literal GitHub CSS.

Use:

- large separation between chapters;
- medium separation between heading and content;
- small separation within related groups.

Whitespace is an intentional interface element.

A deletion/reduction pass is mandatory before a candidate is declared ready.

Target content budget:

- 5 chapters;
- 1 primary hero;
- 0–3 small supporting visual assets maximum;
- approximately 500–750 words;
- zero fake statistics;
- zero imaginary finished repositories;
- zero badge walls;
- zero giant technology inventories.

## 11. Responsive behavior

The profile must remain coherent at:

- wide desktop;
- normal laptop;
- narrow GitHub content width;
- mobile-width rendering.

Narrow behavior requirements:

- no horizontal scrolling caused by README content;
- no squeezed multi-column cards;
- no microtext in raster imagery;
- chapter hierarchy remains intact;
- frame labels wrap cleanly;
- native text carries all critical information;
- image scaling does not make the interface illegible.

Desktop width must add breathing room, not extra clutter.

## 12. Accessibility

The page must practice the standards it names.

Requirements:

- sufficient contrast for amber/gold usage;
- meaningful image alt text;
- important information duplicated in native text where needed;
- no tiny mandatory text embedded in raster assets;
- understandable structure if images fail;
- meaningful link labels;
- hierarchy cannot depend on color alone;
- no decorative motion or animation required for comprehension.

## 13. Public information ceiling

Allowed public content:

- Lucien identity;
- specialization;
- public disciplines;
- system-frame categories;
- selected design principles;
- actual public repositories;
- current public work state;
- Smithy membership.

Do not publish:

- prompts;
- connector mechanics;
- private routing;
- private repository names;
- internal authority implementation;
- private handoffs;
- internal training prompts;
- credentials;
- infrastructure secrets;
- non-public orchestration detail.

The profile is a showcase, not an operating manual.

## 14. Explicitly prohibited design patterns

Reject candidates containing:

- fake GitHub dashboards;
- screenshots masquerading as the final README interface;
- excessive Shields badges;
- four-column Markdown layouts that collapse badly;
- duplicate profile avatar presentation;
- large technology-logo carpets;
- fake project cards;
- imaginary repository counts;
- generated typography used as authoritative copy;
- generated UI labels or generated code text;
- unreadably small text inside images;
- giant biography sections;
- a defensive "still an engineer" essay;
- AI/agent/bot/connector terminology in public copy;
- internal Forge implementation detail;
- arbitrary animation;
- novelty widgets without a user-facing purpose.

## 16. Build sequence

The implementation handoff should require this order:

1. verify exact live authority;
2. inspect current GitHub render constraints;
3. freeze the content skeleton;
4. create clean avatar source;
5. create clean hero source;
6. validate image decoding and repository paths;
7. assemble deterministic hero composition;
8. implement README;
9. verify links and asset paths;
10. inspect desktop render;
11. inspect narrow/mobile render;
12. perform explicit reduction/deletion pass;
13. finalize candidate;
14. return candidate SHA and evidence to Maintainer.

Do not begin by blindly rewriting Markdown.

## 17. Acceptance criteria

A profile candidate is not acceptable unless all of the following pass:

- exact source SHA matched;
- only owned surfaces changed;
- hero file decodes;
- avatar file decodes;
- README-local image references resolve;
- no broken image icon remains;
- no generated textual gibberish remains;
- no false public claims;
- no imaginary finished projects;
- specialization is understandable in the first viewport;
- page remains readable at narrow width;
- hierarchy remains understandable without color;
- amber remains an accent rather than visual spam;
- no badge wall;
- no fake dashboard;
- no private implementation disclosure;
- GitHub still feels like GitHub;
- profile itself demonstrates interface judgment.

Final acceptance question:

> If all explicit UI/UX labels disappeared, would the composition still demonstrate UI/UX judgment?

If no: REWORK.

```text

```

Do not fabricate V2 proof inside V1.
